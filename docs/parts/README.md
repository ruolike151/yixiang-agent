## 为什么这么切

切分依据是 TECH-DESIGN §16.2 的四周计划，而不是按技术分层切。理由是：

1. **每周都有一个能演示的里程碑**——切割点落在"能给别人看"的地方，而不是"某层写完"的地方；
2. **依赖是单向的**——PART 1 → 2 → 3 → 4，后面的部分只消费前面已冻结的接口，不会反向撕扯；
3. **只切 4 块**——每多切一块就多一层"接口文档要同步维护"的成本。这个体量的项目（约 4 周 × 15 小时）超过 5 块就会变成负担。

## 每个部分文档的固定结构

四份文档用同一套骨架，方便你（和未来的协作者）快速定位：

1. **目标与验收**——一句话交付 + 可执行的验收命令，做完就能自己判定"过了没有"；
2. **范围边界**——明确写"本部分不做 X"，防止范围蔓延；
3. **文件清单**——新建/修改哪些文件，与 TECH §1.4 的目录树一一对应；
4. **接口契约**——Consumes（沿用前面什么）/ Produces（向后面承诺什么），含关键签名；
5. **关键设计点**——只放"照着写就不会错"的硬约束，深度算法细节用链接指回 TECH；
6. **任务分解**——按天，每天有产出与验收；
7. **测试与用例**——本部分要覆盖的用例编号（D-xx）；
8. **风险与砍单**——超时先砍什么；
9. **面试讲点**——本部分最容易被追问的地方；
10. **交接检查表（DoD）**——打钩才能进下一部分。

## 怎么用

**开工前**：读本部分的"目标与验收"+"接口契约"，再回 TECH 对应章节看算法细节。不要通读 TECH 全文——它是查阅手册，不是开端到端教程。

**做完后**：过一遍"交接检查表"，全绿才开下一部分。同时把实现中与文档不一致的地方回填到 TECH（对应 §17.3 N-3 的"每周文档回填"约定）。

**面试前**：直接读四份文档的"面试讲点"小节，它们是按"面试官会追问什么"组织的，比通读设计文档高效。

**四份文档之外**：[`../TODO-AFTER-PART-4.md`](../TODO-AFTER-PART-4.md) 是实施过程中攒下的待办
（目前 6 条，全部来自 PART 3 交付时的决策点）。它是**把"当时先这样、以后再说"记在明面上**的地方，
不当设计文档读；触发时机统一是"PART 4 验收通过之后"。
